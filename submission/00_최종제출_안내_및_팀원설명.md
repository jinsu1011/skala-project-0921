### 미흡하거나 확인이 필요한 부분 (중요도 순)

1. **README Contributors 역할이 임시 초안이다 (반드시 수정).** 개발 과정에서 역할을 추정해 적어 둔 것이라 실제와 다를 수 있다. Notion은 "개인별 수행 역할"을 요구하므로 각자 실제로 한 일로 바꿔야 한다. 현재 `<!-- TODO: 팀 확인 필요 -->` 표시가 있다.
2. **평가 결과에 "판단 보류"가 많다.** 근거 부족을 낮은 점수로 바꾸지 않는 설계 규칙(C.5)대로 처리한 결과이지만, 보고서가 얇아 보일 수 있다.
   - TurboQuant 시장성: 기준마다 독립 출처 2계열이 필요한데 부족해 판단 보류
   - ITME 도메인 적합성: 공개 후 3개월이라 기술 고유 근거 부족
   - Judge: TRL·이해관계자는 통과, **시장성·도메인은 재실행 2회 후에도 "판정 불확실"**(보고서 6.2절에 공개)
   - 가설: H1 부분 지지, H2 지지, H3·H4 판단 보류
   - 발표에서는 "억지로 균형을 맞추지 않고 근거 부족을 그대로 드러냈다"로 설명한다(설계 C.2 원칙).
3. **관점 간 상충이 나오지 않았다.** Notion은 "관점 간 상충 지점이 명시적으로 드러나도록"을 요구한다. 설계는 되어 있지만(점수 차 2.0/1.0 판정과 ±0.5 민감도 표), 이번 실행에서 비교할 수 있는 관점 쌍은 모두 "일치"였고 5.2절이 짧다. 질문이 나오면 "판단 보류가 많아 비교 가능한 쌍이 적었고, 기준값을 ±0.5 바꿔도 판정이 바뀌지 않았다(5.5절)"고 답한다.
4. **웹 참고문헌 날짜 형식.** Notion 형식은 `기관명(YYYY-MM-DD). 제목. 사이트명, URL`인데, 웹 34건 중 32건은 게시일을 검색 결과에서 얻지 못해 `(2026-09-22 접속)`으로 적었고, 기관명 대신 도메인(예: deepinfra.com)이 들어간 항목이 많다. 형식은 지켰지만 게시일이 아닌 접속일이라는 점을 알아 두자.
5. **Rubric 사람 점검 칸이 비어 있다.** `docs/RUBRIC_CHECK.md`의 자동 점검(12/12 일치)은 끝났지만, 설계서 C.6이 약속한 "사람이 표본을 확인" 칸은 누군가 원문을 열어 보고 채워야 한다. 시간이 없으면 발표에서 "자동 점검까지 완료"라고만 말한다.
6. **설계서 PDF와 구현이 조금 다르다.** 오전에 제출한 설계서 이후 구현 중 바뀐 7건은 `docs/DECISIONS.md` D44~D50에 기록했다(설계 구현 충실도 항목 대비). 설계서 PDF는 다시 만들지 않았다.
7. **README 샘플의 Usage는 `python app.py`**인데 우리는 `uv run python app.py`이다(uv 환경). 문제는 아니고 README에 설치 순서까지 적어 두었다.

## 3. 팀원 설명 — 우리 시스템이 하는 일

### 한 줄
Google TurboQuant(SW, KV를 작게)와 SK hynix ITME(HW, KV 공간을 넓게)를 TRL·시장·이해관계자·도메인 네 관점에서 평가하되, **어느 쪽이 낫다고 하지 않고** 관점마다 평가가 어떻게 다른지를 근거와 함께 보여 주는 에이전트 시스템이다.

### 흐름 (README의 Architecture 그림 = 실제 코드에서 뽑은 그래프)
1. `initialize` → `index_builder`(논문 6편 PDF → 청크 159개 → bge-m3 인덱스) → `selection_validator`(우리가 고른 두 기술을 논문 근거로 재확인만 함)
2. 공통 검색: `query_planner` → `hybrid_retriever`(한국어 dense + 영어 dense + 영어 BM25, RRF 후 reranker) → `retrieval_grader` → 부족하면 `query_rewriter`로 최대 2번 재검색
3. `tech_research`(기술 개요) → 네 관점 동시 실행: `trl_assessor`, `market_evaluator`, `stakeholder_evaluator`, `domain_evaluator`
4. `synthesizer`(네 관점이 다 끝나면 한 번 실행): 관점 간 점수 차로 상충 판정, H1 격자, 민감도 → 모두 코드 계산
5. `judge`(gpt-4.1)가 관점별 채점 → `retry_router`가 **미달 관점만** 다시 실행(최대 2번)
6. `report_writer` → `final_check`(근거 없는 문장·참고문헌 일치·SUMMARY 분량·우열 표현 검사, 1번 수정) → `pdf_renderer`(SKALA 양식 PDF)

### 발표에서 강조할 차별점 4가지
1. **찬반 양면 검색 + 한 출처 50% 규칙**: 두 기술에 같은 질문 틀, 같은 검색 횟수. 같은 보도자료를 옮긴 기사는 한 출처로 셈. 개발사(Google·SK hynix) 발언은 이해관계자 점수에서 뺌.
2. **Judge 선택적 재실행**: 통과한 관점은 그대로 두고 떨어진 관점만 다시 돌림(`Command(goto)`). 끝까지 미달이면 숨기지 않고 "판정 불확실"로 보고서에 적음.
3. **점수는 코드, 문장은 LLM**: Rubric 점수·상충·H1·민감도는 코드로 계산해서 재현 가능. LLM이 직접 매긴 점수와 비교하면 12개 중 9개만 같았음 → 코드로 강제한 이유.
4. **키 없이 재현**: LLM 응답과 웹 검색 결과를 저장소에 저장 → API 키 없이 `--offline`으로 같은 보고서가 나옴.

### 보고서 핵심 결과 (발표 말미 "핵심 포인트"용)
| | TurboQuant | ITME |
|---|---|---|
| TRL(공개 정보 추정) | 5–7, 신뢰도 높음 | 5–6, 신뢰도 높음 |
| 시장성 | 판단 보류 | 5.00 |
| 이해관계자 | 5.00 | 4.33 |
| 도메인 적합성(W1·W2) | 4.75 | 판단 보류 |

- 점수는 "공개 자료에서 긍정 평가가 얼마나 많은가"를 나타내는 인식 점수이고 기술 품질 점수가 아니다. 두 기술 점수를 서로 비교하지 않는다.
- H1(성숙도와 시장 평가의 방향 차이): 부분 지지. ITME는 TRL 5–6에 비해 시장 평가가 앞서는 "기대 선행" 부분 괴리.
- H2(이해관계자 반응이 생태계 영향을 받음): 지지. ITME 근거는 생태계·전략 언급 비중이 높음.

### Lessons Learned (발표용 요약)
- 여러 에이전트가 같은 근거를 쓸 때 "이 기사가 보도자료 재인용인가" 같은 판단은 한 곳에서 한 번만 해야 한다(처음엔 관점마다 달라 점수가 어긋났음).
- LLM은 숫자를 틀린다 → 수치는 코드가 쓰고, LLM 문장의 수치는 코드 값과 대조해 다르면 뺐다.
- 로컬 임베딩 모델을 병렬 노드가 동시에 쓰면 프로세스가 죽는다 → 검색만 순서대로 처리.
- 근거가 부족하면 부족하다고 쓰는 것이 중립성이다.

### 예상 질문과 답
- "그래서 어느 기술이 나은가?" → 우열을 판정하지 않는 것이 과제 목적. 관점별로 어떻게 달리 평가되는지와 그 조건을 보여 준다.
- "SK 교육과정이 SK hynix 기술을 평가하면 편향 아닌가?" → 같은 질문 틀·검색 한도·Rubric, 개발사 발언 점수 제외, 보고서 6.3절에 편향 가능성 명시.
- "판단 보류가 왜 이렇게 많나?" → 근거가 1계열 이하면 낮은 점수 대신 보류하는 규칙. ITME는 공개 3개월이라 제3자 근거가 적다.
- "Judge도 GPT인데?" → 상위 모델(gpt-4.1)을 썼지만 같은 계열이라는 한계를 명시. 판정의 절반(출처 비중·찬반 계열·금지 어휘)은 코드 검사.
