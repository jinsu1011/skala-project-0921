## 1. Subject · Overview (0:00 ~ 0:40)
`[화면] Subject, Overview`

안녕하세요, 판교 9반 1조입니다. 저희는 KV cache 최적화 기술을 SW와 HW 두 진영에서 하나씩 골라 기술 성숙도, 시장, 이해관계자, 도메인 네 관점에서 평가하는 Agentic RAG를 만들었습니다.

가장 중요한 원칙은 **어느 기술이 낫다고 판정하지 않는 것**입니다. 같은 기술이 관점에 따라 어떻게 다르게 평가되는지를 근거와 조건과 함께 보여 주는 것이 목표입니다. 구조는 LangGraph 기반 멀티 에이전트와 Agentic RAG이고, 결과물인 평가 보고서는 그래프를 실행하면 자동으로 만들어집니다.

## 2. Directory Structure (0:40 ~ 1:00)
`[화면] Directory Structure`

코드는 역할별로 나눴습니다. `agents`에 에이전트, `graph`에 State와 그래프, `tools`에 검색 도구, `rag`에 문서 처리와 검색, `prompts`에 채점 기준 원문이 들어 있습니다. `submission` 폴더에 오늘 제출한 파일을 모아 두었습니다.

## 3. Architecture (1:00 ~ 1:50)
`[화면] Architecture 그림` — 그림의 네 단계 상자를 위에서 아래로 가리킨다

전체 구조입니다. 노드 18개가 네 단계로 나뉩니다. 사람이 기술을 고르면, 첫째 선정 검증과 RAG 준비, 둘째 기술 조사와 네 관점 병렬 평가, 셋째 Judge 검증과 선택적 재실행, 넷째 보고서 생성과 검수 순서로 흐릅니다.

실선은 항상 지나는 길, 점선은 조건에 따라 갈리는 길이고, 마름모는 다음 경로를 정하는 노드입니다. 루프는 네 개이고 모두 횟수 한도가 있어서 반드시 끝납니다. 이 그림은 설계 그림이고, 실제 코드에서 뽑은 그래프도 같은 구조인 것을 확인했습니다. README의 아래 내용도 이 그림 순서를 따라갑니다.

## 4. Selected Technologies — 그림의 "Human 기술 선정" (1:50 ~ 2:30)
`[화면] Selected Technologies`

그림 맨 위의 사람 선정 단계입니다. SW에서는 Google의 TurboQuant를 골랐습니다. 재학습 없이 서빙 중에 KV cache를 양자화해 **데이터를 작게** 만드는 기술입니다. HW에서는 SK hynix의 ITME를 골랐습니다. KV를 줄이지 않고 CXL-hybrid 메모리로 **저장 공간을 넓히는** 기술입니다.

두 기술은 같은 KV cache 용량 문제를 같은 서빙 시점에서 서로 다른 계층으로 풉니다. 그래서 같은 틀로 평가할 수 있습니다. 가이드가 권장한 2안대로 조가 후보 6개를 같은 기준표로 채점해 골랐습니다.

## 5. Tech Stack · Agents (2:30 ~ 3:10)
`[화면] Tech Stack, Agents`

생성 모델은 gpt-4.1-mini, Judge는 그보다 상위인 gpt-4.1입니다. 검색은 FAISS와 BM25를 섞은 3중 하이브리드에 reranker를 붙였고, 42문항 개발 지표로 Hit@5 0.976, MRR 0.863입니다.

에이전트는 가이드의 6개에 Judge를 더해 7개입니다. Judge는 새 내용을 만들지 않고 채점만 해서 다른 에이전트와 역할이 겹치지 않습니다.

## 6. Features — 단계별 동작과 선택 이유 (3:10 ~ 7:00)
`[화면] Features 첫 항목`

이제 그림의 단계를 따라가며 저희가 무엇을 왜 그렇게 했는지 말씀드리겠습니다.

### ① 선정 검증 및 RAG 준비 (3:10 ~ 4:10)
`[화면] ① 선정 검증 및 RAG 준비`

첫 단계에서는 논문 6편, 136쪽을 절 단위로 159개 청크로 나눠 인덱싱합니다. 선정 기술 논문만 넣지 않고 기준선과 대안 논문까지 넣은 이유는 비교할 근거가 필요하기 때문입니다. 선정 검증 노드는 두 기술이 같은 문제를 같은 시점에 다루는지 원문으로 확인해 기록만 합니다.

`[화면] "한→영 교차언어 임베딩" 항목` 여기서 저희 차별점 하나는 **임베딩을 우리 과제 조건으로 직접 평가한 것**입니다. 저희 질문은 한국어이고 논문은 영어입니다. 그래서 논문 청크로 한국어 질문 42개를 만들고, 후보 4종이 정답 청크를 찾는 정확도를 직접 쟀습니다. 리더보드 순위가 아니라 이 측정으로 bge-m3를 골랐습니다. 검색 결과에 기술명이나 수치가 빠지면 질의를 고쳐 최대 두 번 다시 찾습니다.

### ② 기술 조사 및 관점별 병렬 평가 (4:10 ~ 5:40)
`[화면] ② 표`

두 번째 단계에서 네 관점이 동시에 실행됩니다. 이 표가 관점별 평가 기준입니다. TRL은 점수 대신 범위와 신뢰도로 적고, 나머지 세 관점은 가중치를 분석 전에 고정했습니다.

`[화면] "찬반 양면 검색" 항목` 두 번째 차별점은 **찬반 양면 검색과 출처 50% 규칙**입니다. 두 기술에 같은 지지·반대 질의 틀과 같은 검색 횟수를 씁니다. 같은 보도자료를 옮긴 기사는 사이트가 달라도 한 출처로 세고, 한 출처가 절반을 넘지 못하게 합니다. 개발사 발언은 이해관계자 점수에서 뺍니다.

`[화면] "Rubric 기반 코드 채점" 항목` 세 번째 차별점은 **점수와 판정은 코드, 문장은 LLM**이라는 점입니다. 채점 기준을 "긍정 근거 2계열 이상, 부정 없음이면 5점"처럼 근거 개수로 정했고, 근거가 1계열 이하면 판단 보류입니다. 기술 고유 근거는 제목이나 본문에 기술명이 있어야 인정합니다. LLM에게 직접 점수를 매기게 하니 표본 12개 중 4개가 이 규칙과 달라서 코드로 강제했습니다. 네 관점이 끝나면 종합 노드가 상충, 가설 H1에서 H3, 기준값 민감도를 코드로 계산합니다.

### ③ Judge 검증 및 선택적 재실행 (5:40 ~ 6:20)
`[화면] ③`

네 번째 차별점은 **Judge가 기준에 못 미친 관점만 다시 실행하는 구조**입니다. Judge가 네 항목을 채점하고 출처 비중과 찬반 근거 수를 코드로 검사합니다. 떨어진 관점만 `retry_router`가 `Command(goto)`로 다시 돌리고, 통과한 관점은 그대로 둡니다. 두 번 다시 돌려도 미달이면 숨기지 않고 "판정 불확실"로 보고서에 적습니다.

### ④ 보고서 생성·검수 (6:20 ~ 7:00)
`[화면] ④`

마지막 단계에서 보고서를 씁니다. 수치와 표는 코드가 만들고 LLM은 근거 번호가 붙은 해설만 씁니다. 근거 없는 문장, 참고문헌 일치, SUMMARY 반 쪽, 우열 표현을 검사하고 실패하면 한 번 다시 씁니다. `[화면] "종료 보장·재현성" 항목` LLM 응답과 웹 검색 결과를 저장소에 저장해 두어서, API 키가 없어도 같은 보고서를 다시 만들 수 있습니다. 새 폴더에 clone해서 확인했습니다.

## 7. 평가 결과 — 보고서 핵심 포인트 (7:00 ~ 8:40)
`[화면] 평가 결과 표`

보고서 결과입니다. 이 점수는 공개 자료에 나타난 평가의 방향이지 기술의 품질이 아니고, 두 기술을 서로 비교하지 않습니다.

TRL은 공개 정보로 추정한 범위로, TurboQuant 4에서 6, ITME 5에서 6입니다. TRL 4에서 6 구간은 수율과 실측치가 영업 비밀이라 공개 정보가 가장 적습니다.

TurboQuant는 시장성 4.45, 이해관계자 5.00, 도메인 4.78로 세 관점이 모두 일치했습니다. 가설 H1은 부분 지지입니다. TurboQuant는 성숙도에 비해 시장 기대가 앞선 "기대 선행"으로 나왔습니다. H2는 기각입니다. 두 기술 모두 이해관계자들이 생태계보다 기술 자체를 더 많이 이야기했습니다.

ITME는 이해관계자 4.50 외에 시장성과 도메인이 판단 보류입니다. 올해 6월에 공개돼 ITME를 이름으로 언급한 제3자 자료가 아직 적기 때문입니다. 그래서 Judge에서도 TRL, 시장성, 도메인이 두 번 재실행한 뒤에도 "판정 불확실"로 남았고, 보고서 한계점에 그대로 적었습니다.

## 8. Lessons Learned (8:40 ~ 9:40)
`[화면] Lessons Learned`

배운 점은 세 가지입니다.

첫째, **기준은 코드로 확인할 수 있어야 지켜집니다.** "기술 고유 근거만 센다"는 규칙을 LLM에게만 맡겼더니, ITME를 언급하지도 않는 다른 기술 논문이 ITME 근거로 붙었습니다. "제목이나 본문에 기술명이 있어야 한다"는 확인 가능한 조건으로 바꿨습니다.

둘째, **판정은 코드, 문장은 LLM입니다.** LLM이 가설을 "지지"로 판정하면서 근거 문장에는 "비슷하다"고 쓴 경우가 있었고, 요약에서 TRL 수치를 틀린 경우도 있었습니다. 수치와 판정은 코드가 만들고 LLM 문장은 코드 값과 대조하도록 했습니다.

셋째, **근거가 부족하면 부족하다고 쓰는 것이 중립입니다.** 모든 관점을 통과시키려고 기준을 낮추지 않았습니다.

## 9. 마무리 (9:40 ~ 10:00)
`[화면] Usage`

실행은 `uv sync` 후 `uv run python app.py`이고, API 키 없이도 `--offline`으로 같은 보고서가 나옵니다. 감사합니다.

## 예상 질문 (발표 후 질의응답)
- **어느 기술이 더 나은가요?** → 우열을 판정하지 않는 것이 과제 목적입니다. 같은 기술이 관점에 따라 어떻게 달리 평가되는지와 그 조건을 보여 드립니다.
- **SK 교육과정이 SK hynix 기술을 평가하면 편향되지 않나요?** → 두 기술에 같은 질문 틀·검색 한도·Rubric을 썼고, 개발사 발언은 점수에서 뺐습니다. 소속에 따른 편향 가능성은 보고서 6.3절에 적었습니다.
- **판단 보류가 많은데 보고서로서 의미가 있나요?** → 근거가 1계열 이하인데 점수를 주면 확인되지 않은 평가를 만드는 것입니다. 어디에 근거가 부족한지도 의사결정에 필요한 정보이고, ITME는 공개 3개월이라는 조건도 함께 적었습니다.
- **Judge도 같은 GPT 계열 아닌가요?** → 상위 모델을 썼지만 같은 계열이라는 한계를 보고서에 적었습니다. 판정의 절반인 출처 비중·찬반 근거 수·금지 어휘는 코드 검사입니다.
- **왜 Send가 아니라 Command를 썼나요?** → Send로 부른 노드는 넘겨준 값만 받아서 기술 개요와 근거 목록을 읽지 못합니다. Command(goto)는 전체 State를 읽은 채로 해당 관점 노드만 다시 실행합니다.
