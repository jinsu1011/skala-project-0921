## 0. 한 줄 소개 (0:30)
- KV cache 병목을 SW로 푸는 Google TurboQuant와 HW로 푸는 SK hynix ITME를 TRL·시장·이해관계자·도메인 관점에서 평가하는 Agentic RAG. **우열·추천이 아니라 관점별 평가 차이와 그 근거를 추적**한다.
- 에이전트 7개, 노드 18개, State 키 27개, 루프 4개(모두 한도 있음). README의 Architecture 그림은 실제 컴파일된 그래프이다.

## 1. 차별점 (4:00)
1. **찬반 양면 검색 + 원 출처 계열 50% 규칙** (1:00)
   - 두 기술에 같은 지지·반대 질의 템플릿, 같은 검색 한도(최초 1회 + 재질의 2회).
   - 같은 보도자료를 옮긴 기사는 도메인이 달라도 한 계열(`origin_group`). 재인용 판단은 문서마다 한 번 해서 모든 관점이 같은 값을 쓴다(D50).
   - 개발사(Google·SK hynix) 발언은 이해관계자 점수에서 제외.
2. **Judge 선택적 재실행** (1:00)
   - Judge(gpt-4.1)가 설계서 D.5 판정식 그대로(`LLM_OK and COMMON and PER_PERSPECTIVE`) 채점.
   - `retry_router` 노드가 미달 관점만 `Command(goto=[노드명])`로 다시 실행. `Send`를 쓰지 않은 이유: Send로 부른 노드는 `tech_brief`·`evidence`를 못 읽음.
   - 통과 관점은 동결, 한도(2회) 후에도 미달이면 "판정 불확실"로 보고서 한계점에 기록.
3. **점수는 코드, 해설은 LLM** (0:40)
   - C.6 Rubric 근거 조건(긍정 2계열 이상·부정 없음 = 5 …)을 코드로 계산. 상충(2.0/1.0), H1 3×3 격자, ±0.5 민감도도 코드.
   - LLM 판정이 근거 문장과 어긋난 사례(H2)가 있어 H1~H3 판정은 코드로 옮겼다.
   - "기술 고유 근거"는 제목·본문에 기술명이 있어야 인정(무관한 논문이 근거로 붙던 문제를 코드 규칙으로 차단).
4. **한→영 교차언어 임베딩 자체 평가** (0:40)
   - 42문항으로 후보 4종 비교 → bge-m3. 개발 지표(구현 조건): Hit@1 0.786, Hit@5 0.976, MRR@10 0.863.
   - 측정 중 입력 길이 잘림을 발견해 구현 조건(2,048)으로 재측정. 설정 선택과 성능 보고를 같은 42문항으로 했다는 한계도 공개.
5. **키 없이 재현** (0:40)
   - LLM 응답·웹 검색 결과를 저장소에 커밋 → `uv run python app.py --offline`이 API 호출 0회로 같은 보고서 생성. 키가 없으면 자동 전환.

## 2. 보고서 핵심 포인트 (4:00)
- **TRL(공개 정보 기반 추정)**: TurboQuant 4–6(신뢰도 높음), ITME 5–6(신뢰도 보통). TRL 4~6 구간은 공개 정보가 가장 적다는 점을 함께 말한다.
- **관점별 점수(인식 점수, 품질 점수 아님)**: TurboQuant 시장성 4.45·이해관계자 5.00·도메인 4.78 / ITME 이해관계자 4.50, 시장성·도메인 판단 보류.
- **판단 보류의 의미**: 근거가 1계열 이하인 기준은 낮은 점수가 아니라 보류. ITME는 공개 후 3개월이라 "ITME"를 이름으로 언급한 제3자 자료가 적다.
- **가설**: H1 부분 지지(TurboQuant 기대 선행), H2 기각(두 기술 모두 기술 언급이 생태계 언급보다 많음), H3 판단 보류(TurboQuant는 기각 쪽, ITME 근거 부족), H4 부분 지지.
- **Judge 결과**: 이해관계자 통과, TRL·시장성·도메인은 재실행 2회 후에도 "판정 불확실". 숨기지 않고 6장에 그대로 실었다.
- **상충**: 비교 가능한 관점 쌍은 모두 일치. 기준값을 ±0.5 바꿔도 판정이 바뀌는 칸 수를 5.5절에 공개.

## 3. Lessons Learned (1:30)
- **공유 근거의 속성은 한 곳에서 정해야 한다**: 관점마다 재인용 여부를 따로 판정하자 같은 기사가 관점별로 다른 계열로 세어졌다. 문서 단위 판정으로 바꾼 뒤 Rubric 점검이 12/12로 맞았다.
- **병렬 노드와 로컬 모델**: 관점 4개가 MPS 위의 임베딩·reranker를 동시에 호출하자 프로세스가 죽었다. 검색만 직렬화했다(D48).
- **LLM 수치 실수는 코드로 막는다**: SUMMARY에서 TRL 범위를 틀리게 쓴 사례 → SUMMARY 수치 줄은 State에서 생성하고, 서술 문장의 TRL 수치는 코드 값과 대조해 다르면 뺀다.
- **정직한 한계 보고**: 모든 관점을 통과시키려 기준을 낮추지 않았다. ITME 근거 부족은 판단 보류·판정 불확실로 남겼다.

- Q. SK 교육과정이 SK hynix 기술을 평가하는 편향은? → 같은 질의 틀·검색 한도·Rubric, 개발사 발언 점수 제외, 6.3절에 소속 편향 가능성 명시.
- Q. Judge가 같은 GPT 계열인데? → 상위 모델(gpt-4.1)을 썼지만 같은 계열이라는 한계를 6.3절에 적었다. 판정의 절반(출처 비중·찬반 계열·어휘)은 코드 검사이다.
