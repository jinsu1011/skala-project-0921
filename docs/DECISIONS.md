# Decision Log

형식: **결정 / 근거 / 검토한 대안**

## 설계 단계 (2026-09-21)

**D1. 기술 선정은 Human 기반(2안)으로 하고 에이전트는 사후 검증만 한다.**
- 근거: 에이전트가 고르면 최신 자료 편중과 비교 계층 불일치 위험이 있다. 사람이 선택하되 `selection_validator`가 원문 근거로 검증해 추적성을 확보한다.
- 대안: (1안) 선정 에이전트. 실행마다 선정 결과가 달라져 설계서와 보고서가 어긋날 위험이 있고, 에이전트가 하나 늘어난다.

**D2. SW는 TurboQuant, HW는 ITME로 한다.**
- 근거: 가중 기준표(공정성 35, 근거 25, 산업 25, 최신 15)에서 진영별 최고점이다(4.60 / 4.50. v1.1에서 TurboQuant 4.35로 정정 → D17). 두 기술 모두 모델을 바꾸지 않는 서빙 계층 기술이다.
- 대안: MLA(사전학습이 필요해 제외 조건 ③), InfiniGen(2.95), CXL-PNM(2.90).

**D3. TRL은 기술 조사 Agent가 맡고, 별도 노드 `trl_assessor`로 분리해 Fan-out에 넣는다.**
- 근거: 원 논문을 이미 읽는 에이전트라 성숙도 근거를 보기에 자연스럽다. 노드를 분리하면 Judge가 TRL만 선택적으로 재실행할 수 있다. `tech_research`에 두면 재실행 때 Fan-out 전체가 다시 돈다.
- 대안: 독립 TRL 에이전트(불필요한 에이전트 증가), `tech_research` 내부 처리(선택적 재실행 불가).

**D4. Judge 에이전트를 추가한다(총 7개).**
- 근거: 중립성, 인용, 출처 다양성을 코드 수준 품질 게이트로 보장하고 Loop와 Branch의 근거를 만든다. 새 사실을 만들지 않으므로 역할이 겹치지 않는다.
- 대안: 평가 종합 에이전트에 통합(생성자와 검증자가 같아져 자기평가 편향 발생).

**D5. `document_loader`를 `index_builder`에 합친다.**
- 근거: 로드, 페이지 한도 확인, 청킹, 인덱싱이 한 번에 실행되는 결정적 단계라 분리해도 얻는 것이 없다. 그래프 높이도 줄어 가독성이 좋아진다.
- 대안: 팀 초안의 분리 구조. State 키 `document_manifest`는 그대로 두고 작성 노드만 바꾼다.

**D6. 보고서 검수(`final_check`)를 PDF 렌더링보다 먼저 한다.**
- 근거: 마크다운 단계에서 인용, 형식, 우열 표현을 고치는 편이 싸고, 불필요한 PDF 재생성을 피할 수 있다.
- 대안: 팀 초안(PDF → 검수 → 재작성).

**D7. `human_review`는 기본 실행에서 경고만 남기고 진행한다. `--interactive`일 때만 `interrupt`한다.**
- 근거: 채점자가 명령 한 줄로 재현할 수 있어야 한다.
- 대안: 항상 사람 입력을 기다림(자동 재현 불가).

**D8. 임베딩은 `BAAI/bge-m3`로 한다.**
- 근거: 자체 교차언어 평가(42문항)에서 Hit@1/3/5와 MRR이 모두 1위이고, SW·HW 균형도 가장 좋다. MIT 라이선스이다. (v1.0에 "1,024 토큰을 받아 청크 전체를 수용"이라고 썼으나 1,024는 평가 설정값이었고 일부 청크가 잘렸음 → D20에서 정정)
- 대안: Qwen3-0.6B(팀 초안 가정. MRR 0.631, HW 0.493으로 편차 큼), e5-large(512 토큰 제한), MiniLM(128 토큰 제한).

**D9. 검색 구성은 3중 RRF(Dense KO + Dense EN + BM25 EN)에 bge-reranker-v2-m3를 붙인다.**
- 근거: MRR이 0.703(dense)에서 0.790(3중 RRF), 0.863(+rerank)으로 올랐다. 보고서 생성은 배치 작업이라 질의당 4.7초 지연을 수용한다.
- 대안: dense 단독, 2중 RRF(MRR 0.786), `--no-rerank` 옵션으로 제공.

**D10. Qwen3는 모델 카드의 기본 `query` 프롬프트로 비교한다.**
- 근거: 직접 만든 지시문(0.548)보다 성능이 좋아(0.631), 후보마다 최적 설정으로 비교하는 것이 공정하다.
- 대안: 직접 만든 지시문(불리한 조건).

**D11. 평가셋 영어 재작성은 질문만 보고 생성 모델이 만든다.**
- 근거: 정답 청크를 본 LLM이 재작성하면 누설로 BM25 점수가 0.816으로 부풀려진다. 런타임 `query_rewriter`와 같은 조건으로 측정해야 한다.
- 대안: QC 단계에서 재작성(폐기).

**D12. 청크는 900 토큰, 겹침 15%, 절 경계 우선으로 한다. 참고문헌은 제외하고 부록은 유지한다.**
- 근거: 팀 설계(800~1,000 토큰, 15%)를 따른다. 참고문헌 청크는 검색 잡음을 만든다. 부록에는 실험표가 많아 유지한다.
- 대안: 페이지 단위 청킹(절 정보 손실).

**D13. arXiv PDF는 커밋하지 않고 다운로드 스크립트만 둔다.**
- 근거: 재배포 라이선스가 불명확하다. `scripts/download_papers.py`가 페이지 수까지 검증한다.
- 대안: PDF 커밋.

**D14. Mermaid는 mermaid.js를 vendoring하고 헤드리스 Chrome으로 로컬 렌더링한다.**
- 근거: mermaid.ink 같은 외부 서비스로 다이어그램을 업로드하지 않는다. 오프라인에서도 재현할 수 있다.
- 대안: mermaid.ink API(외부 전송이라 정책상 차단됨), mermaid-cli(puppeteer Chrome을 추가로 다운로드해야 함).

**D15. 산출물 PDF는 SKALA 공식 docx 양식을 python-docx로 채우고 LibreOffice로 변환한다.**
- 근거: 제출 양식을 준수한다(사용자 요청). 맑은 고딕이 없는 환경에서는 PDF 변환 때만 Apple SD Gothic Neo로 대체한다.
- 대안: HTML → Chrome PDF(양식 미준수).

**D16. 팀 가설 4개와 초기 가설 4개를 H1~H4로 통합한다. "우위로 지목", "순위 비교" 표현은 "평가 방향이 엇갈림"으로 바꾼다.**
- 근거: 우열 판정 금지 원칙(Notion). 초기 H1·H2(배포 용이성, 무손실 용량)는 도메인 기준과 H4에 흡수했다.
- 대안: 가설 8개(보고서 분량 과다), 팀 원문 그대로(순위 비교는 우열 판정으로 읽힘).

## 설계 개정 v1.1 (2026-09-21, 교수님 피드백 반영) — 상세 비교는 `docs/REVISION_v1.1.md`

**D17. TurboQuant 근거 점수를 4에서 3으로 내린다(가중합 4.60 → 4.35).**
- 근거: ITME(벤더 단일 출처 → 3점)와 대칭을 맞춘다. 설계 시점에 확보한 TurboQuant 자료도 논문과 블로그 모두 Google 자료이다. 선정 결과는 바뀌지 않는다.
- 대안: 4점 유지(B의 "변경 금지"). 대칭성 위반이라 기각했다.

**D18. 임베딩 선정을 3단계(사전 적합성 → 과제 실험 → 운영 판단)로 재구성하고 v1.0의 가중 기준표를 삭제한다.**
- 근거: 필수 조건과 가중합이 한 절에 공존해 모순이었다. 기존 측정값은 그대로 유지한다.
- 대안: C1 방식("세 가지 필수 조건" 서술 + 가중표 유지). 모순이 남아 기각했다.

**D19. 진영 간 균형을 `min(SW MRR, HW MRR)`로 정의하되 "사후 정의"로 명시한다.**
- 근거: 실제로는 측정 후 정의했으므로, "사전 기준"으로 쓰면 사실과 다르다. 이 기준을 빼도 결론(전체 지표 1위)은 같다.
- 대안: 사전 기준으로 기재(피드백 지시). 사실 왜곡이라 기각했다.

**D20. 모델 고유 최대 입력과 평가 설정을 분리하고, 평가 시 잘린 청크 수를 공개한다. 구현 `max_seq_length`는 2,048로 한다.**
- 근거: config로 확인한 모델 한계는 bge-m3 8,192, Qwen3 32,768, e5 512, MiniLM 128이다. 청크 900은 cl100k 기준이라 모델 토크나이저로는 최대 1,529토큰이다.
- 대안: 재측정(B의 "새 실험 금지"에 따라 이번 개정에서는 하지 않고 향후 계획으로 둠).

**D21. 관점 점수는 분석 전에 고정한 가중치로 계산한다. 근거 수는 신뢰도에만 쓰고, 근거 부족 기준은 "판단 보류"로 처리한다. 이해관계자·도메인 환산 규칙을 추가하고, TRL은 상충 판정에서 분리해 H1 전용 사전 규칙으로만 쓴다.**
- 근거: 웹 자료가 많은 기술이 구조적으로 유리해지는 비대칭을 없앤다. 척도가 달라 H1이 기계적으로 지지되는 것도 막는다.

**D22. 출처 50% 규칙에 분모(최신 결과의 웹 근거 ID), eTLD+1 정규화, 벤더 출처군을 정의하고, `scope` 태그로 category 근거의 찬반 할당량 인정을 막는다.**
- 근거: 공개 후 기간이 짧은 ITME에 CXL 일반 비판을 끌어오는 거짓 균형을 방지한다.

**D23. `retry_router`를 노드로 두고 `Command(update, goto=[Send…])`를 반환한다. `judge`는 채점만 하고 `judge_feedback`을 신설한다.**
- 근거: LangGraph 조건부 엣지 함수는 State를 갱신할 수 없다. reducer가 없는 키는 단일 작성자 원칙을 따른다(`selection_override`, `rewritten_queries` 신설).

**D24. `human_review` 재확인은 최대 1회로 제한한다. 그림은 2a(전체)와 2b(품질 제어 상세)로 나누고, mermaid 소스는 부록 A로 옮긴다.**
- 근거: "모든 루프에 한도" 문장과 일치시키고, 100% 배율에서의 가독성을 확보한다(2a 약 7.7pt).

**D25. Judge 판정은 `all(LLM 4항목 ≥ 4) and 출처군 ≤ 50% and pro ≥ 2 and con ≥ 2 and 우열 어휘 = 0`으로 한다. 표현은 "교차 모델"에서 "상위 모델"로 바꾼다.**
- 근거: 합계 조건만으로는 결정적 검사가 빠진다. 생성과 채점 모델이 같은 GPT-4.1 계열이라는 한계를 명시한다.

## 설계 개정 v1.2 (2026-09-21, 2차 리뷰 반영)

**D26. 기술 선정은 2안(Human)만 그래프에 반영한다. `human_review` 재선정 분기와 관련 키 2개를 삭제한다.**
- 근거: 선정 주체는 사람이다. 에이전트는 검증 결과만 기록하고, 선정 변경은 팀이 실행 밖에서 `--tech`로 한다. 루프가 5개에서 4개로, State 키가 29개에서 27개로 준다. D7과 D24의 `human_review` 관련 부분을 대체한다.
- 대안: 대화형 재확인 유지. 1안(에이전트 개입)처럼 읽힐 여지가 있고 재현성을 해쳐 기각했다.

**D27. 비교 공정성 기준 문구를 "같은 적용 계층"에서 "동일한 적용 시점(추론·서빙 단계)"으로 바꾼다.**
- 근거: 두 기술은 계층이 다르고(데이터 표현 vs 메모리) 시점이 같다. 2.1.3의 공정 비교 논리와 일치시킨다.

**D28. 구현 조건(`max_seq_length` 2,048)으로 v2 재측정을 하고, v1 수치는 보존한다. 모든 수치는 "개발 지표"로 표기한다.**
- 근거: 채택 설정의 성능을 확인해야 한다(2차 리뷰). 로컬 연산만 사용했고 추가 LLM 판정은 하지 않았다(하한값). 결과는 순위 불변, 채택 구성 수치 동일이다.
- 대안: 판정 이력이 없는 쌍 추가 판정(약 $0.5). 채택 구성 top-5에 영향을 줄 수 있는 쌍이 5쌍뿐이라 보류했다.

**D29. reranker는 2중·3중 하이브리드 모두에 적용해 보고하되, 채택은 v1에서 고정한 3중 구성을 유지한다.**
- 근거: v2에서 reranker 이전에는 2중 RRF가 앞섰지만(0.786 vs 0.778), reranker 이후 두 구성의 값이 같다. 결과를 보고 구성을 사후에 바꾸지 않는다.

**D30. 출처 독립성 단위로 `origin_group`(원 출처 계열)을 도입하고, 임계값은 heuristic임을 명시하며 ±0.5 민감도를 보고하고, Agent와 Node를 정의한다.**
- 근거: 도메인이 달라도 같은 보도자료를 재인용한 기사는 독립 근거가 아니다. 임계값을 객관적 사실처럼 보이지 않게 하고, 발표 때 받을 "에이전트·노드 수" 질문에 대비한다.

## 설계 개정 v1.3 (2026-09-21, 문서 구조)

**D31. 설계서 본문을 Notion 산출물 요구 순서(A 대상 기술 → B 설계 → C 평가 관점 및 기준 → D 그래프 설계 → E 보고서 목차)로 재배열하고 부록을 없앤다.**
- 근거: 채점자가 요구 항목을 순서대로 대조할 수 있게 한다.
- 재배치: 분석 배경은 A.1, 문제 정의·범위는 C.1(도메인 선정과 함께), 설계 단계 검증 현황은 B.9, 리스크는 D.6으로 옮긴다. 그림 2a의 mermaid 소스는 D.3 본문에 넣는다(Notion D: "Graph 흐름 설계(mermaid)"). 개정 이력은 `docs/REVISION_v1.1.md`로만 유지한다.
- E는 표만 있던 구성을 **실제 목차(장·절)** + 원천 State 표 + 작성 규칙으로 보강한다.
- 그림은 노드 여백·간격을 줄여 인쇄 글자 크기를 키운다(2a 약 10pt, 2b 약 8pt). 그림 2a는 캡션과 함께 한 페이지에 싣는다. 내용·수치 변경은 없다.

## 설계 개정 v1.4 (2026-09-21, 3차 리뷰·과제 안내 보완 반영) — 항목별 처리 결과는 `docs/REVISION_v1.4.md`

**D32. `final_check`에 한도 소진 출구를 추가한다. 노드는 늘리지 않는다.**
- 근거: 수정 한도(1회)를 쓴 뒤에도 검수에 실패하면 갈 곳이 없었다. 결정적 후처리(우열 어휘 치환, SUMMARY 절단, 근거 없는 문장 삭제) 후 남은 위반을 `warnings`에 기록하고 `pdf_renderer`로 간다. 모든 루프가 "통과"와 "한도 소진" 두 출구를 갖는다.
- 대안: 후처리 전용 노드 추가(노드 19개가 되어 설계서 전반의 수치가 바뀜).

**D33. 선택적 재실행은 `Send`가 아니라 `Command(goto=[관점 노드명])`로 한다. D23의 `Send` 부분을 대체한다.**
- 근거: `Send`로 호출된 노드는 전달한 인자만 입력으로 받아 `tech_brief`·`evidence`를 읽을 수 없다. `judge_feedback`는 이미 State에 있으므로 노드명으로 보내면 된다. `retry_router`는 `Command[Literal[...]]` 반환 타입으로 목적지를 선언해 렌더링에 출구가 나타나게 한다. 그림 2a의 가짜 노드(R1~R4)를 없애고 실제 관점 노드로 점선을 되돌렸으며, `retry_router`·`final_check`는 사각형(라우팅 노드)으로 그린다.
- 대안: `Send`에 전체 State를 실어 보냄(병렬 복사본 간 reducer 병합이 복잡해짐).

**D34. 실행 시 `recursion_limit` 50을 명시하고 LangGraph를 1.2.x로 고정한다.**
- 근거: 최악 경로가 약 30 superstep이다. 리뷰 의견은 "기본값 25를 넘는다"였으나, 설치 버전(1.2.11)의 기본값은 10,007로 확인했다(`langgraph/_internal/_config.py`). 이 경우 기본값은 이상 동작을 막는 상한이 되지 못하므로, 버전과 무관하게 50을 명시한다.

**D35. 관점 에이전트 내부 Loop는 노드 내부 로직으로 유지한다(subgraph로 분리하지 않음).**
- 근거: 노드 18개와 State 27개의 계약, 그리고 `Command(goto)` 재실행 경로를 그대로 둘 수 있다. Loop는 그림 2b(b), 프롬프트, `audit_log`(라운드별 질의·근거)로 확인하고, 캡션에 "실제 그래프 렌더링에는 나타나지 않음"을 명시한다.

**D36. H1은 3×3 격자로 판정하되, 리뷰안의 "해당 없음" 칸 대신 "부분 괴리"를 둔다.**
- 근거: 이전 규칙(두 조건 괴리)으로는 가설 후반부(실측 검증된 기술의 채택 신호 지연)를 판정할 수 없었다. 리뷰안 격자는 한 칸 어긋난 경우 중 (중간 TRL, 시장 ≤ 2.0)만 "괴리"이고 (중간 TRL, 시장 ≥ 4.0)은 "해당 없음"이라 방향에 따라 대우가 달랐다. 대각선 거리(0 일치, 1 부분 괴리, 2 괴리)로 정의하면 두 방향이 대칭이 되고, 가설 두 절을 모두 판정할 수 있다. 경계값은 ±0.5 민감도 점검에 포함한다.
- 대안: 리뷰안 그대로(비대칭), 이전 규칙 유지(가설 절반 판정 불가).

**D37. Judge 결정적 검사를 관점별로 나누고, 개발사 발언을 이해관계자 점수에서 빼며, 비교 대상에 대한 서술은 서술 주체를 밝힌다.**
- 근거: TRL은 찬반이 아니라 단계 추정이므로 찬반 할당량 대신 범위 상·하한 근거(`bound_origins`)를 본다. 개발사의 자기 평가가 인식 점수에 들어가면 벤더 편향이 그대로 점수가 된다. A.5의 "KIVI는 생성 토큰을 양자화하지 않는다"는 TurboQuant 저자의 서술이며, KIVI 논문(p.5)은 최근 잔차 토큰만 원정밀도로 두고 나머지는 그룹 단위로 양자화한다고 서술하므로 두 서술을 함께 적었다.

**D38. 상충·H1 판정은 `synthesizer` 안에서 코드로 계산하고, Judge 재채점은 재실행된 관점과 synthesis 해설로 한정한다(통과 관점 동결).**
- 근거: 판정이 재현 가능해지고 synthesis 오류의 처리 경로가 정해진다(해설 문장만 unsupported 처리, 재실행 분기 없음). 동결은 LLM 출력의 흔들림으로 통과한 관점이 다시 미달되는 것을 막는다. 관점당 검색 라운드 상한은 9회(3라운드 × 3회 실행)이다.

**D39. 검색 구성은 3중 RRF + reranker를 유지한다. reranker 지연은 회차별 값을 모두 공개한다. 사전 적합성 길이 조건은 모델 토크나이저 단위로 쓴다.**
- 근거: reranker 적용 후 2중과 3중은 v1·v2 모두 네 지표가 같다. 3중은 reranker 이전 v1 측정(MRR 0.790 vs 0.786)으로 먼저 고정했으므로, 동률을 확인한 뒤 바꾸면 사후 선택이 된다(D29 유지). 지연은 v1.0 첫 측정 4.7초(커밋 2b77d77), v1.2 재실행 4.5초, v2 4.7초이다. v1.2 재실행 때 v1 CSV의 지연 열이 덮어쓰였음을 여기에 밝힌다(정확도 열은 같음. 원 값은 git 이력에 있음). 리뷰안의 "4.7초(v1) / 4.5초(v2)"는 버전이 뒤바뀐 것이라 따르지 않았다. 길이 조건은 "모델 토크나이저 기준 최대 청크 1,529토큰 이상"으로 바꿨고 판정 결과는 같다.
- 대안: 2중으로 교체(리뷰 권장안, 절약성 근거). 동률 처리 규칙을 사전에 정하지 않았으므로 사후 교체로 읽힐 수 있어 기각했다.
- 그 밖에 리뷰안 중 "Mermaid 소스를 부록으로 이동"은 따르지 않았다. Notion 요구 항목이 "Graph 흐름 설계(mermaid)"이고 부록을 없앤 구조(D31)이므로 D.3 본문에 둔다. 파일명은 이미 Notion 형식(`RAG-Design_판교-9반_…`)이다.

**D40. 도메인은 데이터센터·클라우드 장문맥 LLM 서빙 1개로 한정하고, 관점별 채점 Rubric을 정의한다(과제 안내 보완).**
- 근거: 과제 안내에서 도메인을 하나만 선정해 잘 정리하라고 했다. 도메인을 늘리면 시장·이해관계자 조사 범위도 함께 늘어난다. 온디바이스 대조군을 없애고, H3는 같은 도메인 안의 워크로드(W1 장문맥 배치 vs W2 고동시성 다중 턴) 비교로 바꿨다. W1·W2는 도메인 적합성 채점에만 쓰는 평가 조건이다. 또한 평가 기준은 에이전트가 참고할 Rubric이어야 한다는 안내에 따라, 점수 앵커(1~5, 판단 보류)와 기준별 긍정·부정 신호를 C.6에 정의하고, 개발 중 사람이 표본 점검해 `docs/RUBRIC_CHECK.md`에 기록한다.

## 개발 착수 전 수정 (2026-09-22)

**D42. `index_builder`를 `selection_validator`보다 먼저 실행한다.**

## 개발 단계 (2026-09-22)

**D44. `final_check`가 수정 한도 소진 후 결정적 후처리를 할 때 `report_markdown`·`references`를 직접 고친다.**

**D45. 인식 점수는 C.6 근거 조건으로 코드가 계산하고, LLM은 근거마다 긍정·부정 신호를 표시하고 이유를 쓴다.**

**D46. 원 출처 계열(`origin_group`)은 등록 도메인·벤더 계열 사전으로 정하고, 보도자료 재인용 여부는 관점 에이전트의 근거 표시(`republished_vendor`)와 동일 제목 규칙으로 판단한다.**

**D47. 공통 검색 품질 판정(`retrieval_grader`)은 코드 규칙으로 한다.**
- 근거: B.5-4의 판정 항목(기술명, 원리, 수치나 한계)은 문자열·정규식으로 확인할 수 있어 LLM 호출 없이 재현 가능하게 판정한다.

**D49. `docs/graph.png`는 `draw_mermaid()` 결과에서 defer 노드용 표시 엣지 2개를 지우고 로컬 렌더링한다.**

**D50. 보도자료 재인용 여부(원 출처 계열)는 근거 문서마다 한 번, 제목과 주소만 보고 판정해 모든 관점이 같은 값을 쓴다.**
- 근거: 처음에는 관점 에이전트가 근거 표시 단계에서 재인용 여부를 함께 적었는데, 같은 기사를 관점마다 다르게 판정해 원 출처 계열이 관점별로 달라졌다. 그 결과 `docs/RUBRIC_CHECK.md` 표본 점검에서 에이전트 점수와 재계산 점수가 3건 어긋났다. 판정을 문서 단위 캐시 호출(`tools/evidence.py` `rereport_family`)로 옮긴 뒤 12/12건 일치했다. 웹 발췌문은 질의마다 달라지므로 판정 입력에서 뺐다. 공유 근거를 병합할 때 한 관점이라도 재인용으로 본 문서는 개발사 계열로 둔다(보수적 병합).
